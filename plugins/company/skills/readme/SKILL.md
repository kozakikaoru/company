# ポートフォリオ用 README 作成 — `/company:readme`

採用担当・仲介エージェント・他の開発者が読む想定の **ポートフォリオ用 README** を作る。エンドユーザー向けの宣伝文ではない。「派手なアピールではなく、実用品を真面目に作った」という素朴で誠実な印象を狙う。

## 起動時の流れ

1. リポジトリから抽出できる情報を集める (package.json / 主要な設定ファイル / ディレクトリ構成 / 使用フレームワーク・言語・DB・テスト)
2. 不足している **必須情報** だけをユーザーにテキストで確認する (下記)
3. `docs/README-draft.md` に草案を書き出す (本物の `README.md` は上書きしない)
4. 全文を提示して「直したい箇所があれば指摘して」と添える
5. ユーザーが「OK、本物に反映して」と言ったら、`README.md` へ反映 + `docs/README-draft.md` 削除 + PR 作成

## 抽出・確認する情報

**必須** (無ければユーザーに聞く):
- プロジェクト名 (タイトル)
- サービス概要 (1 行、三人称で)
- 技術スタック (フレームワーク / 言語 / DB / テスト等 — package.json 等から自動抽出を優先)

**あれば良い** (リポジトリから拾えれば使う、無ければ省略):
- 特徴を抽象化する材料 (機能リスト、解決する課題、UX 上の工夫)
- 画面イメージ (`docs/images/` 配下の画像パス)
- 実装上の工夫 (設計判断、トレードオフ、独自の最適化)
- 環境変数の定義 (`.env.example` 等から)
- ディレクトリ構成 (`tree -L 2 src/` 等で取得)
- プライバシー・データ方針 (個人情報を扱うサービスなら)

## トーン・文体の必須ルール

| 項目 | ルール |
|---|---|
| 二人称 | 「あなたの」を使わない。利用者向け文章ではないので三人称的に書く |
| 数値・実装詳細 | 具体数値 (「35 問」「10 立場」等) や内部コンポーネント名を本文に出さない。本質を抽象的に書く |
| 重複表現 | 同じ意味の語の繰り返しを避ける (例:「7 段の段階」) |
| 括弧の順序 | 「日本語名(英語/URL/パス)」の順。◯「プライバシーポリシー(`/legal/privacy`)」/ ✗「`/legal/privacy`(プライバシーポリシー)」 |
| 誇張表現 | 「最強」「圧倒的」「世界初」などを使わない。素朴に |
| 弱い訴求 | 「匿名 OK」のような弱い特徴は載せない (削る判断をする) |
| 工夫の主体 | 実装上の工夫は **作者本人が判断・工夫したこと** として書く。「AI が作った/工夫した」体裁にしない (主語は作者) |
| 絵文字 | 基本使わない。必要なら見出しではなく本文の一部に控えめに |
| 不要セクション | 「このプロジェクトについて」「謝辞」「ライセンス」は基本入れない (個人ポートフォリオでは無くて困らない) |

## 構成テンプレート (基本この順番)

以下のセクション順で書く。各セクション間には水平線 `---` を入れる。

- `# {タイトル}` — 直後に 1 行のサービス説明 (三人称)
- `## 特徴` — 箇条書き 5 項目程度。数値・実装詳細を出さず本質を抽象的に。機能の羅列でなく「何が嬉しいか」を読み手の言葉で
- `## 画面イメージ` — あれば。テーブル 1 行 × N 列 (`| 画面1 | 画面2 |` の下に `| ![](./docs/images/01-xxx.png) | ... |`)。枚数は 2〜4 枚で可変、内容の薄い画面 (設定画面等) は無理に入れない。画像は縦横比・サイズを揃える
- `## 技術スタック` — 「レイヤー / 採用技術」の 2 列テーブル (フレームワーク・UI・言語・DB・テスト等)。続けて `### 実装上の工夫` を箇条書き 3〜5 項目。採用担当が判断材料にできる粒度で、主語は作者本人 (「設計した / 分離した / 重視した」等)、内部実装名はファイルパス参照程度に控えめに
- `## ローカル起動方法` — `bash` コードブロックで「依存インストール → 環境変数 (あれば `cp .env.example .env.local`) → 開発サーバー起動 → `http://localhost:{port}`」。直後にデフォルト動作の説明 1〜2 行と Runtime バージョン要件。必要なら `### 環境変数` を「変数 / 必須 / 例・既定 / 説明」のテーブルで
- `## コマンド一覧` — `bash` コードブロックで主要コマンドを短コメント付き
- `## ディレクトリ構成(抜粋)` — コードブロックで重要な階層だけ、コメントで中身を短く
- `## プライバシー / データ方針` — 個人情報を扱うサービスなら必須。何を保存し何を保存しないか、ログ方針、検索エンジン除外、同意・レート制限などを箇条書き

## 出力ルール

- 草案は **`docs/README-draft.md`** に書き出す。本物の `README.md` は直接上書きしない
- markdown としてちゃんとした見た目に。各セクション間に水平線 `---`
- 画像は `![](./docs/images/xxx.png)` 標準構文
- コードブロックの言語指定 (` ```bash ` / ` ```ts ` 等) を正しく付ける
- 長すぎない。読み手が数分で全体像を掴める分量に

## 完成後の振る舞い

- 草案の全文を提示 + 「直したい箇所があれば指摘して」と一言添える
- 指摘があれば修正 → 再提示
- ユーザーが「OK、本物の README.md に反映して」等と承認したら:
  1. `README.md` に反映
  2. `docs/README-draft.md` を削除
  3. `docs/readme-portfolio` 等のブランチを切る
  4. commit メッセージは `docs(readme): README をポートフォリオ用に再構成` の形式
  5. PR を作成し、URL を返す (タイトル・説明は日本語)

## 秘書ちゃんモードとの連携

秘書ちゃんモード (`/company:secretary`) 中に「README 作って」「ポートフォリオ用の README を」等と言われたら、このスキルのルールに沿って生成する。プロジェクトの `.company/state.md` に仕様・技術スタックが記録されていれば、それを優先的に材料として使う (聞き直しを減らせる)。
